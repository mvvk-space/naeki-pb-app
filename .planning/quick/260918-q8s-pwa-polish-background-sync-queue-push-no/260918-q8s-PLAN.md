# Quick Task: PWA polish — background sync queue, announcements, share target + install

Goal: make the two shells survive a dead network and feel like a real installed app —
offline submissions queue durably and drain on reconnect, an honest announcements feed
pairs with a service-worker notification path, and the installed app appears in the OS
share sheet with an in-app install affordance.

Reality this plan designs against (do not re-litigate):

- `src/sw.js` is the **only** service worker the PWA loads (Electron never loads one).
  `src/public/sw.js` + `src/public/manifest.webmanifest` are a **stale build artifact
  dir** — out of scope, do not edit.
- Renderer is plain IIFEs attached to `window`, bundled by `src/entry.js`. CSP in
  `src/index.html` is `default-src 'self'` — **no inline scripts/styles**, only class
  swaps / CSSOM for dynamic styling.
- `src/store.js` already best-effort pushes the owner blob to `/api/state`
  (`schedulePush`, debounced 120 ms) and loyalty via `persistLoyalty()` — both currently
  **drop the write on failure** with a console warning. That is the seam the queue fills.
- `server/api.ts` (Drizzle, live) and `server/api.mjs` (legacy twin that `main.js`
  actually spawns) carry the same routes and must stay in sync.
- There is **no** VAPID/web-push infrastructure and the repo ethos is "nothing is sent
  anywhere". So: build the real SW `push` + `notificationclick` handlers, drive display
  from a polled announcements feed + an explicit permission affordance, and say so
  honestly in the UI copy. Do **not** build a push server.

Tasks are **sequential** (they share `src/sw.js`, `src/index.html`, `src/app.js`).

## 1. Durable offline queue + Background Sync (SW wakes, client drains)

The offline story today "ends at the fallback page". Give it a memory.

**Files**

- `src/queue.js` *(new)* — `window.NaekiQueue`, own IIFE, same shape as the other modules
- `src/sw.js` — `sync` handler + `queue.js` in the `SHELL` precache list
- `src/entry.js` — import `./queue.js` after `api.js`, before `store.js`
- `src/store.js` — enqueue instead of dropping on failed `userStateUpsert` / `upsertLoyalty`
- `src/app.js` — register replay handlers, wire flush triggers, offline checkout copy, chip
- `src/index.html` — `#queue-chip` in `.side-foot` (hidden unless pending)
- `src/styles.css` — `.queue-chip` (reuse existing chip/token recipes, no new palette)
- `tests/unit/queue.test.mjs` *(new)*

**Action**

- `src/queue.js`: durable queue in its **own** localStorage key (`naeki.queue.v1`, shape
  `{entries: [{id, kind, key, payload, ts, attempts, lastError, dead}]}`) so it can never
  be clobbered by the `store.js` blob merge. Expose:
  - `enqueue(kind, payload, {key, coalesce})` — dedupes by `key` while a same-key entry is
    pending; `coalesce: true` replaces the payload in place (the newest full blob is the
    only one that matters for state/loyalty pushes).
  - `register(kind, handler)` — handler returns `{ok, retry}`; `retry === false` →
    dead-letter (`dead: true`, kept for inspection, excluded from `flush`).
  - `flush({force})`, `pulse()` (flush only when `navigator.onLine`), `pending()`,
    `pendingCount()`, `onChange(fn)`, `clear()`.
  - `MAX_ATTEMPTS = 6`; on failure `attempts++` + `lastError`, entry **kept**. Nothing is
    ever silently dropped.
- `src/store.js`: `schedulePush`'s `if (!ok)` branch and its `.catch` become
  `window.NaekiQueue?.enqueue("state", owned, {key:"state", coalesce:true})`; wrap
  `persistLoyalty()` the same way with `{key:"loyalty", coalesce:true}`. `signOut()` gets
  one `flush({force:true})` attempt before dropping the token; leftovers stay queued for
  the next sign-in (handlers return `retry:false` while `!API.me()`).
- `src/app.js` handlers: `state → API.userStateUpsert`, `loyalty → API.upsertLoyalty`,
  `draft → API.promoCreate` with `{key: "draft:" + draftId}` (dedupe = the
  "idempotent-ish" guarantee: one pending submission per draft, never two creates).
- `src/app.js` flush triggers: `window.addEventListener("online", …)`,
  `visibilitychange` when visible, and a `navigator.serviceWorker` `message` listener for
  `naeki:flush-queue`. After an offline enqueue, register
  `reg.sync.register("naeki-queue")` guarded by `"sync" in reg` (Electron/Safari have no
  Background Sync — the online + visibility triggers are the graceful path).
- `src/sw.js`: `self.addEventListener("sync", …)` for tag `naeki-queue` →
  `clients.matchAll({includeUncontrolled:true, type:"window"})` → `postMessage({type:"naeki:flush-queue"})`.
  The page does the writes; the SW only wakes it. Say exactly that in the comment.
- `src/app.js` checkout handler (`#cart-checkout`, ~line 1451): after a successful
  receipt, when `!navigator.onLine` → `flash("Saved on this device — syncing when you're back online")`
  and `NaekiQueue.pulse()`. Paint `#queue-chip` ("⟳ N waiting to sync") from `onChange`.
- `tests/unit/queue.test.mjs` via `makeSandbox({files:["api.js","queue.js"]})`: enqueue→flush
  drains and clears; a throwing handler keeps the entry and bumps `attempts`; `retry:false`
  dead-letters; same-key coalesce keeps one entry with the newer payload; `flush()` is a
  no-op when `navigator.onLine = false` unless `force`; a fresh sandbox seeded with the
  persisted key still sees the entries (durability).

**Verify**

```bash
npx vitest run tests/unit/queue.test.mjs && npm test
npm run check && npm run lint
```

**Done**

Queue is durable across reload, dedupes/coalesces by key, never drops an entry silently;
an offline checkout keeps its receipt and leaves exactly one queued push; `online`,
`visibilitychange` and a Background Sync wake all drain it; Electron (no SW) still drains
via the online/visibility path.

## 2. Announcements: minimal table, public read route, SW notification display

Pair the polish with an announcements table — keep it small.

**Files**

- `db/app-schema.sql` — `announcement` table + index
- `db/schema.ts` — Drizzle twin
- `db/announcement-data.sql` *(new)* — idempotent seed (`insert … on conflict do nothing`)
- `server/api.ts` — `GET /api/announcements`
- `server/api.mjs` — same route, `pg` twin
- `src/api.js` — `announcementList({branch, since})`
- `src/store.js` — `announcementSeen: []` + accessors
- `src/app.js` — poller, render, permission affordance, notification relay
- `src/index.html` — `#rw-announcements` + `#ann-toggle` block in the Offers pane
- `src/sw.js` — `push`, `notificationclick`, and `naeki:announce` message → `showNotification`
- `tests/unit/announcements.test.mjs` *(new)*

**Action**

- Schema (both files, identical shape — `db/app-schema.sql` stays the applied source of
  truth): `announcement(id text pk, title text not null, body text, branch text,
  url text, created_ms bigint, published boolean not null default true)` plus
  `announcement_published_idx on (published, created_ms desc)`. `branch` null = all branches;
  `url` null = open the app. Nothing else.
- Route (both servers): `GET /api/announcements?branch=<name>&since=<ms>` — **public read**,
  `where published and (branch is null or branch = $branch) and created_ms > $since`,
  `order by created_ms desc limit 20`, camelCase rows (`{id,title,body,branch,url,created}`).
  No auth, no writes — the table is seeded, not user-writable.
- `src/api.js`: `announcementList({branch, since})` following the `stockList` convention —
  **`null` when the backend is unreachable** (the PWA served over http(s) from a phone
  cannot reach `127.0.0.1:8090`; that must degrade quietly, not throw).
- `src/app.js`: poll every 60 s + on `online`, branch-filtered by the first subscribed
  branch. Render the feed into `#rw-announcements` (kicker "Announcement", branch name or
  "All branches", `fmtAgo` timestamp, optional link via the existing `data-external` path).
  New ids (not in `announcementSeen`) are marked seen and *displayed*: prefer
  `navigator.serviceWorker.ready → active.postMessage({type:"naeki:announce", announcement})`
  when `Notification.permission === "granted"`, fall back to `new Notification(...)` in a
  `try/catch`, and always `flash()` in-app. Empty/unreachable → quiet "No announcements
  right now." (never an error state).
- Permission affordance: `#ann-toggle` in the Offers pane. Click → `Notification.requestPermission()`;
  granted → hide the button, copy "Announcements on — this device shows them while the app
  is open."; denied → point at browser settings. When `!("Notification" in window)` the
  button is replaced by honest copy: no server push exists here, announcements arrive when
  the app is open, and real web-push needs VAPID keys + an https origin. No invented
  push backend.
- `src/sw.js`: real `push` handler (`e.data.json()` parsed defensively, `showNotification`
  with `title/body/tag/icon` and `data:{url}`), real `notificationclick` (focus an existing
  window or `clients.openWindow`), and a `message` handler for `naeki:announce` that calls
  `registration.showNotification`. Comment states plainly: the `push` path is future-ready
  for a real web-push service; today the page relays to it via `postMessage`.
- `tests/unit/announcements.test.mjs` (`makeSandbox({files:["api.js"]})`, `sb.fetch` override
  like `stock-api.test.mjs`): rows map to the UI shape; `?branch`/`?since` land in the query
  string; a dead backend returns `null`, not `[]` or a throw; non-2xx returns `null`.

**Verify**

```bash
psql "$(cat ~/.config/neon/naeki-sushi.dsn)" -v ON_ERROR_STOP=1 \
  -f db/app-schema.sql -f db/announcement-data.sql
npm run api &  # :8090
curl -s "http://127.0.0.1:8090/api/announcements" # → {"items":[…]}
npx vitest run tests/unit/announcements.test.mjs && npm test
npm run check && npm run lint
```

**Done**

`announcement` exists in both schema surfaces; both servers serve the public read route;
`api.js` maps it and returns `null` when unreachable; the Offers pane renders the feed and
offers a real permission affordance with honest copy; the SW has working `push` /
`notificationclick` / relay handlers; no push server was invented.

## 3. Share target + install prompt + version surfaces

Make the installed app reachable from the OS share sheet, and installable deliberately.

**Files**

- `src/manifest.webmanifest` — `share_target` (GET), keep every existing field
- `src/index.html` — `#lp-install` button in the landing header; `#ch-shared` share-inbox block in the Chat view
- `src/app.js` — share intake + inbox render, `beforeinstallprompt` flow, iOS fallback
- `src/store.js` — `shareInbox: []` + `shareInboxAdd` / `shareInboxState` / `shareInboxClear`
- `src/styles.css` — styles for the two new blocks (existing card/chip recipes)
- `scripts/validate.mjs` — enforce the `share_target` contract
- `src/sw.js` (`VERSION`), `main.js` (`?v=` query), `package.json` (`version`) — one lockstep bump
- `tests/unit/share-inbox.test.mjs` *(new)*

**Action**

- Manifest `share_target`: `action: "./index.html?share=1"`, `method: "GET"`,
  `enctype: "application/x-www-form-urlencoded"`, `params: {title, text, url}`. GET (not
  POST) on purpose: it needs no SW interception and survives on any http(s) host, which is
  exactly the deployment the PWA already documents. Keep `display: "standalone"`,
  `start_url`, `scope`, icons untouched. No `id`/`display_override` churn.
- `src/app.js` share intake on boot: when `share=1`, read `title`/`text`/`url` from
  `location.search`, `S.shareInboxAdd({title, text, url, ts})`, prefill `#ch-input` with the
  text (or title/url) when the Chat composer exists, `flash("Shared to Naeki — saved on this
  device")`, then `history.replaceState` to drop the query so a reload doesn't re-add it.
  `#ch-shared` in Chat renders the inbox newest-first ("Shared from your phone", `fmtAgo`,
  link-out for a URL) with a Clear button. Local only — same ethos as the chat draft.
- Install prompt: capture `beforeinstallprompt` (`e.preventDefault()`, stash the event,
  unhide `#lp-install`); click → `prompt()` → await `userChoice` → hide, `flash` the
  outcome; `appinstalled` → hide + "Installed — Naeki is on your home screen". iOS fallback:
  no `beforeinstallprompt` **and** `/iPhone|iPad|iPod/.test(navigator.userAgent)` **and** not
  already installed (`display-mode: standalone` or `navigator.standalone`) → show the button
  labelled "Add to Home Screen", whose click flashes the Share-sheet instructions. Electron
  and non-promptable desktop browsers: the button stays hidden, no error path.
- `scripts/validate.mjs`: in the existing manifest block, `problem()` unless
  `share_target.method === "GET"` and all three `params` (`title`/`text`/`url`) are present
  with an `action` ending in `index.html?share=1`. `npm run check` then fails loudly if the
  share contract is broken.
- Version surfaces: bump in lockstep because the shell changed (index.html markup, SW
  precache list, manifest): `package.json` `2.14.0-journal → 2.15.0-pwa`,
  `src/sw.js` `VERSION = "2.15.0-pwa"`, `main.js` `?v=2.15.0-pwa`. Nothing else.
- `tests/unit/share-inbox.test.mjs` (`makeSandbox({files:["store.js"]})`): add → newest
  first; entries survive a reload through the localStorage seed; blank input is rejected;
  clear empties it.

**Verify**

```bash
npx vitest run tests/unit/share-inbox.test.mjs && npm test
npm run check && npm run lint && npm run check:mobile
# manual (PWA): cd src && python3 -m http.server 8000 → install button appears in Chrome,
# the app appears in the OS share sheet, a shared URL lands in the Chat share inbox.
```

**Done**

Manifest declares a valid GET `share_target` and `npm run check` enforces it; a shared
URL/text opens the app, prefills the chat composer, and lands in a durable on-device share
inbox; the install button is visible only when the browser offers a prompt (or on iOS with
honest Add-to-Home-Screen copy) and hides after install; all three version surfaces read
`2.15.0-pwa`.

## Security notes

- `/api/announcements` is a new **unauthenticated** read route — it must filter on
  `published = true` in SQL (never in the client) so drafts are not enumerable, and it stays
  read-only (no POST/PATCH), consistent with `/api/coupons`.
- The SW `push`/`message` handlers must treat the payload as untrusted: parse
  `e.data.json()` defensively, coerce `title`/`body` to strings, and only ever use a
  same-origin `url` for `notificationclick` — never `clients.openWindow` on an
  attacker-supplied absolute URL.
- The queue holds user-owned blobs (order history, wallet) in localStorage exactly as
  `store.js` already does — no new exposure, and no new outbound destination: replay targets
  the same `/api/state`, `/api/loyalty`, `/api/promos` the app already calls.
- No new dependencies, so the package-legitimacy gate does not apply.

## Non-goals (do not build)

- No VAPID keys, no web-push server, no APNs/FCM bridge (README's "future path" stays true).
- No IndexedDB-backed SW replay; Background Sync wakes the page, the page writes.
- No edits to `src/public/*` (stale build artifacts) and no `src/public` refresh.
- No POST share target, no server-side share inbox, nothing about shares leaves the device.
